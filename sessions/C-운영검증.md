# 세션 C — 운영·검증

**소유 파일**: 새 검증 스크립트 (`scripts/` 아래)
**작업대**: **원본 폴더** (읽기 위주) — 유일하게 `data/`에 접근한다
**성격**: 재고, 대조, 데몬 운영. **다른 세션의 손발이자 감시자.**

## ★ G11이 왜 이 세션의 존재 이유인가

지금 우리 검증은 **전부 '이전 우리 값'과 비교**한다.
`연속 3구간 0건`도 `법원별 수집 급감`도 그렇다.
**처음부터 적게 긁고 있었으면 영원히 모른다.**

2026-09-16에 찾은 rowspan 버그가 정확히 그랬다 —
매각결과 표에서 **페이지마다 첫 물건이 조용히 사라지고 있었는데** 아무 경고도 안 울렸다.

법원이 공식 매각통계를 준다(`PGJ164M01`). **바깥 기준선을 만들면 그때부터 조용한 손실이 사라진다.**

## 묶음 F — 계산만 미리 해둘 것

지금 고치지는 않는다. 다만 **숫자는 준비해둔다.**

- 하루 8사이클 중 **6개가 매일 신규 0·변경 0~16**
- **매각결과를 사이클마다 통째로 재수집** — 7일치 9,000건을 하루 8번
- **`days_until_sale`이 오늘 날짜로 계산**되어 자정마다 전량 재푸시
  (한 사이클 4,513건 / 280MB / 483초)
- 상세 수집기는 **할 일이 없는데** 1분마다 같은 34건 재시도

**줄이기 전에 반드시 계산할 것**: `apply_lifecycle` 주석이
*"수집이 하루 4~5회 도니 7일이면 30회 가까이 연속 미목격"*을 전제한다.
하루 2회면 14회가 된다. **그리고 제약선은 [G16](../gaps/G16-문서-조회창.md)이다** —
낙찰가 7일, 문서 1~2주. **며칠까지 멈춰도 되는지의 답이 거기 있다.**

## 자주 쓰는 조회
```bash
# 사이클별 요약 — 법원별 0건 패턴까지
grep -E "물건 수집 완료|매각결과|인기도|토지이용|생명주기|웹 푸시" logs/collect-all.log | tail

# 데몬 상태
launchctl list | grep court-auction
```

## 함정
- **DB 시각은 전부 UTC**다. KST와 9시간 차이라 "9시간째 멈춘 것처럼" 보이기 쉽다.
- 숫자를 볼 때 **활성 / 활성+미래기일 / 활성+좌표**를 구분한다. 웹 목록 수는 마지막 것.
- 어제 이전 로그는 `logs/archive/`에 있다. **아무것도 지우지 않는다.**
- **4GB DB에 `detail_json LIKE '%...%'`는 몇 분 걸린다.** 파이썬으로 한 번만 훑는 편이 낫다.
- 상세 수집기 성적은 **재시작 직후 수치로 판단하지 말 것.** 세션이 상하는 데 몇 시간 걸린다.

## 공통 규칙 (모든 세션)

1. **한 파일은 한 세션만 만진다.** 남의 파일이 필요하면 그 세션에 요청한다.
2. **코드를 고치는 세션은 워크트리로 격리한다.** 단 격리 작업대엔 `data/`가 안 따라온다 —
   `--db data/auction.sqlite3` 기본값이 cwd 상대경로라 **에러 없이 빈 DB가 새로 생긴다.**
   **DB 조회·수집 명령·데몬 재시작은 세션 C에 부탁한다.**
3. **문서는 `cat >`로 쓰지 말 것.** 남의 세션이 같은 파일을 만들었을 수 있다.
   덧붙일 때는 앵커를 찾아 끼워 넣는다. (2026-09-16에 이걸로 사고 한 번 냈다)
4. **일이 끝난 브랜치는 그때그때 main에 넣는다.** 안 그러면 다음 워크트리가 낡은 코드에서 시작한다.
5. **푸시는 사용자 승인.** 커밋까지는 알아서.
6. **일이 끝나면 `DEVLOG.md` 맨 위에 기록.** 다른 세션이 아는 유일한 통로다.
7. **코드를 고쳐도 데몬은 모른다.** `launchctl kickstart -k gui/$(id -u)/com.court-auction.<이름>`
