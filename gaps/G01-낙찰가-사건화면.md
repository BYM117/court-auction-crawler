# G01. 낙찰가를 '사건 종국 전까지' 받을 수 있는데 안 읽는다

**상태**: **코드는 끝났다** (A가 구현·가동 중) · 남은 것은 수집이 도는 시간뿐 · **담당**: 세션 A
**묶임**: G04 · G05와 **같은 데이터에서 나온다. 한 번에 파싱할 것.**

## 한 줄
매각결과 화면(7일 창) 말고도 **사건 화면에 낙찰 금액이 남아 있다.** 회수 가능한 것이 1,451건.

## 원인
법원 상세는 두 갈래로 들어온다. 우리는 물건 단위(`detail_json['sections'|'tables']`)만 읽고,
사건 단위(`detail_json['case']`)는 **받아만 놓고 안 읽는다.**

```
detail_json['case']['case_tables']                 사건 기본내역
detail_json['case']['filing_and_service_tables']   문건처리 내역 · 송달내역
detail_json['case']['schedule_tables']             사건 기일내역
```

사건 기일내역 행(7칸):
```
[물건번호, 감정평가액, 기일(시각), 기일종류, 기일장소, 최저매각가격, 기일결과]
["2","304,000,000원","2025.12.11(10:00)","매각기일","경매법정 4별관 211호","20,891,000원","매각(21,000,000원)"]
["2","304,000,000원","2025.12.18(14:00)","매각결정기일","3층 7호법정 4별관","최고가매각허가결정"]
["2","304,000,000원","2026.01.27(16:00)","대금지급기한","민사집행과 경매11계","납부(2026.01.20)"]
```

물건 단위 기일내역(5칸)에는 금액이 없다. 그래서 "기일내역엔 금액이 없다"고 잘못 결론냈었다.

## 결과 (실측 2026-09-16)

매각결과 화면 값과 겹치는 699건을 대조했다.

| | 건수 |
|---|---|
| 금액 일치 | **699** |
| 금액 불일치 | **0** |
| 우리 DB에 물건은 있는데 결과행 없음 | **1,451 ← 회수 가능** |
| 우리 DB에 물건 자체가 없음 | 2,789 |

참고로 유찰 기준 '진짜 놓친 결과'가 336건이었다. **상세 경로가 그보다 훨씬 많이 회수한다.**

## 창(窓) — '영구'가 아니다

경매사건검색 화면 유의사항:
> *"부동산은 검색은 되나 **사건이 종국되면 기일관련 정보를 제공하지 않고**, 이후 30일이
> 지나면 기본정보 만을 제공합니다."*

실측으로 확인했다 — 취하로 종국된 평택지원 2024타경1116은 `기일정보`·`최근입찰결과`가 **공란**이다.
우리 DB의 `종국결과`가 전수 55,345건 **전부 `미종국`** 인 것도 같은 이유다(활성 물건만 상세를 받으니까).

**창은 7일이 아니라 '사건 종국까지'** 다. 낙찰 → 대금납부 → 배당 → 종국이 보통 2~6개월이다.
**미종국일 때 걷어둬야 한다.**

## 고치는 법 — 함정 두 개를 먼저 알 것

**① 표가 세 리스트에 흩어져 있다.**
실측 500건에서 `매각(N원)` 행은 전부 `filing_and_service_tables`의 `기일 내역`에 있었다.
그런데 다른 물건에서는 `schedule_tables`에 있다.
**리스트 이름을 믿지 말고 세 개를 다 훑고 caption으로 찾을 것.**

**② 행의 첫 칸은 "이 물건"의 번호가 아니다.**
사건 단위 표라서 형제 물건이 섞인다. 실측: 3,029개 행 **전부**가 이 물건의 물건번호와 달랐다.
당연하다 — 낙찰된 물건은 사이트에서 사라지고 우리가 들고 있는 건 그 형제니까.

→ **`(법원, 사건번호, 행의 물건번호)`로 item_key를 새로 만들어 붙일 것.**
이걸 안 하면 0건이 나오거나(필터가 다 막음) 엉뚱한 물건에 남의 낙찰가가 붙는다.

**③ 뽑을 것**
`기일결과`에서 `매각(N원)` · `납부(날짜)` · `최고가매각허가결정` · `최고가매각불허가결정`.

## 확인
```sql
SELECT COUNT(*) FROM auction_items WHERE detail_json LIKE '%"매각(%원)"%';
-- 4,756건. 그 안의 낙찰가 행 18,444개(중복 포함), 기일 범위 2023.03.06 ~ 2026.09.08
```

---

## ★ 확인 (2026-09-17, 세션 B) — 이미 만들어져 돌고 있다

B가 이 묶음을 집으면서 보니 **알맹이가 이미 있다.**

```
detail_crawler.parse_case_schedule()  → store.backfill_sale_results()
```

상세 수집기가 사건 화면에 들를 때마다 기일내역을 읽어 `auction_sale_results`에
없는 행만 채우고, 마지막 기일이 낙찰이면 물건의 `sold_amount`·`sold_date`를 세운다.
되살아난 물건을 옛 낙찰로 다시 내리지 않는 가드도 들어 있다. 세션 A가 2026-09-17
밤새 이 경로로 **낙찰가 808건(2,025억)** 을 건졌다(`DEVLOG`).

현재: `auction_sale_results` 48,830행, 그중 금액이 붙은 것 9,713행.

**B가 할 코드 일은 없다.** 남은 것은 상세 수집기가 아직 안 들른 사건을 도는 시간이다.
사건이 종국되면 창이 닫히므로(위 '창' 절) 수집기를 세워 두지 않는 것이 이 격차의 관리법이다.
