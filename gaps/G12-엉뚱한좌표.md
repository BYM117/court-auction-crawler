# G12. 토지 449건이 지도에서 엉뚱한 곳에 찍혀 있다

**상태**: 진행 중 (C 진단 2026-09-17 · B 코드 수정·교정 실행 2026-09-17) · **담당**: 세션 B · **우선순위**: 최상위 급
**성격**: G01~G16 중 **유일하게 '틀린' 데이터**다. 나머지는 '없는' 데이터다.

## 한 줄
빠진 핀은 정직하지만 **잘못 찍힌 핀은 거짓말이다.**

## 원인 — 재현되는 한 줄

```python
>>> from court_auction_crawler.geocoder import _extract_building_hint
>>> _extract_building_hint('전라남도 여수시 삼산면 덕촌리 1069 [토지 전 3498㎡]')
'전라남도'          # ← 건물명이 아니라 시도 이름이 나온다
```

`geocoder._try_place_search`는 지번 검색이 실패하면 건물명 장소검색으로 폴백한다.
```python
building = _extract_building_hint(address)
tokens = ... normalized.split()
for width in (3, 2):
    query = " ".join([*tokens[:width], building]).strip()
```

건물명이 없는 **순수 토지 물건**에서 `_extract_building_hint`가 토큰을 역순으로 훑다가
끝까지 가서 **첫 토큰(시도명)** 을 돌려준다. 그래서 쿼리가:
```
전라남도 여수시 삼산면 + 전라남도  →  "전라남도 여수시 삼산면 전라남도"
```

브이월드는 이 쿼리를 그 읍면의 어떤 기본 지점으로 해석한다.
**같은 읍면의 모든 토지가 같은 좌표를 받는다.**
`_same_region()` 가드는 지역이 실제로 맞으므로 통과시킨다.

## 결과 (실측)

| | 건수 |
|---|---|
| `coordinate_source='building'` | 활성 1,041 / 비활성 727 |
| 그중 쿼리가 시도명으로 끝남 = 망가짐 | **활성 449 / 비활성 244** |
| 망가진 활성 449건이 찍힌 서로 다른 좌표 | **191개** (평균 2.35건이 한 점) |
| 한 점에 뭉친 최대 | **13건** (34.0253, 127.314653 — 여수 삼산면) |

주소가 전부 다른 13건이 소수점 6자리까지 똑같은 한 점에 있다.

원본 주소 vs 정규화 주소 대조:

| | verified 30,130 | approximate 1,041 |
|---|---|---|
| 일치 | 81.4% | 31.9% |
| 지번이 다름 | 0.8% (236) | 24.2% (252) |
| **동/리가 다름** | **0.5% (147)** | **22.1% (230)** |

```
인천 서구 가좌동 146-44 영동빌라   →  인천 서구 심곡동 329-9
영암군 삼호읍 삼포리 1886-12       →  영암군 삼호읍 나불리 1086
영암군 삼호읍 용당리 789           →  영암군 삼호읍 나불리 1086   ← 다른 물건이 한 점으로
함평군 나산면 우치리 629           →  함평군 나산면 삼축리 323-1
```

**웹은 이걸 구분하지 못한다.** `coordinate_quality`가 payload에는 실리는데
(`enrichment.py:164, 338`) 웹 저장소에서 쓰는 곳이 없다.
**approximate 핀이 verified 핀과 똑같이 보인다.**

## ★ 진단 (2026-09-17, 세션 C) — 원인이 둘이었고, 큰 쪽은 코드 문제가 아니다

### ① 표본 50건을 **그대로 다시 돌렸더니 48건(96%)이 정상 좌표를 얻었다**

코드를 한 줄도 안 고치고, 지금 있는 `geocode_address`를 그대로 불렀다.


**틀린 핀은 평균 2km 떨어져 있었고, 지금 코드로는 제대로 찍힌다.**

### ② 왜냐면 — 망가진 좌표의 78%가 **고치기 전에** 찍혔다

| 좌표가 찍힌 달 | 건수 |
|---|---|
| **2026-07** | **813** |
| 2026-08 | 176 |
| 2026-09 | 52 |

광주·전남 통합 대응(`MERGED_SIDO`)은 **2026-08-24 `ebbf640`** 에 들어왔다.
그 전에 찍힌 813건은 *"그때 브이월드가 `전라남도 …`를 못 찾아서"* 폴백으로 샌 것이다.
**지금은 찾는다.** 실측:

```
전라남도 영암군 삼호읍 용당리 789
  → 주소검색 PARCEL '전라남도 영암군 삼호읍 용당리 789'
      → 전남광주통합특별시 영암군 삼호읍 용당리 789 (34.753193, 126.389250)  same_region=True
  DB에 들어 있는 값: 나불리 1086 (34.777372, 126.464115)   ← 2.3km 떨어진 가짜
```

**한 번 좌표가 박히면 다시 안 물어본다.** `geocode-missing`은 *좌표가 없는* 물건만 본다
(`cli.py:225`). **틀리게 있는 것은 영원히 안 고쳐진다.** 이게 진짜 구조적 문제다.

### ③ 그래도 버그는 살아 있다 — 9월에 52건이 새로 생겼다

통합 대응이 들어온 뒤에도 52건이 같은 방식으로 망가졌다.
`_extract_building_hint`가 행정구역명을 돌려주는 문제는 **그대로다.**
실제로 지금도 안 풀리는 것이 있다:

```
충청북도 음성군 대소면 삼호리 790   → 주소검색·getcoord 네 번 모두 '없음'
충청북도 음성군 대소면 부윤리 166-1 → 네 번 모두 '없음'
```
이런 것들이 폴백으로 흘러가 같은 점에 뭉친다. 표본 50건 중 2건(4%)이 여기 해당한다.

### ④ 후보 쿼리가 잘리는 문제는 **아니었다**

`max_queries=4`(`geocoder.py:98`)가 지번 후보를 잘라내는 줄 알았는데, 재보니
448건 중 **0건**이 잘렸다. 토지 주소는 대개 정규화하면 후보가 1~2개뿐이라 상한에 안 닿는다.
**이 가설은 버려도 된다.**

## 고치는 순서 — 진단 결과에 맞춰 (2026-09-17)

**재시도가 제일 싸고 제일 크다. 다만 순서를 지켜야 한다.**

1. **`_extract_building_hint`가 행정구역명을 못 돌려주게 막는다.** (작은 변경)
   먼저 해야 한다 — 안 그러면 재시도에서 실패하는 4%가 **다시** 가짜 좌표를 받는다.
2. **1,041건의 좌표를 지우고 재시도 대상으로 돌린다.** 96%가 정상 좌표를 얻는다.
   `geocode-missing`이 좌표 없는 것만 보므로, 지우면 기존 경로가 알아서 집어간다.
   **DB 쓰기라 세션 C에 부탁할 것.**
3. **그래도 못 찾으면 좌표를 안 만든다.** 마지막 수단이지 1차 대안이 아니다.
4. **한 번 박힌 좌표를 다시 안 물어보는 구조 자체**를 볼 것. `approximate` 품질은
   기한을 두고 재시도하는 게 맞다. 이번 건은 그 구조가 없어서 두 달을 방치했다.
5. (세션 D) 웹이 `coordinate_quality`를 쓰게 한다.

## ★ 고침 (2026-09-17, 세션 B) — 원인이 하나 더 있었다

### ① 진짜 원인은 **읍면 승격**이었다

`_extract_building_hint`가 시도명을 돌려주는 것은 **새는 구멍**이었고, 애초에
지번 검색이 왜 실패했는지가 원인이다. 실측:

```
충청북도 음성군 대소면 성본리 577-2  → 브이월드 네 번 모두 '없음' → 폴백이 가짜 좌표
충청북도 음성군 대소읍 성본리 577-2  → 36.962750, 127.528336 (지번 일치)
```

대소면이 **대소읍으로 승격**됐다. 법원은 옛 이름을, 지도는 새 이름을 쓴다.
`MERGED_SIDO`(시도)·`RENAMED_SIGUNGU`(시군구)는 보정하면서 **읍면은 아무도 안 봤다.**
그 면의 토지가 전부 지번 검색에 실패해 폴백으로 샜다. 같은 면의 다른 물건이
같은 점에 뭉친 이유이기도 하다.

`apply_swapped_eup_myeon`으로 읍↔면 두 이름을 다 던진다. 승격은 계속 일어나므로
목록을 두지 않는다. 후보 상한에 잘리지 않게 시군구 개명보다 앞에 놓는다.

### ② 핀을 없애는 것은 답이 아니다

> 사용자 지침(2026-09-17): "못 찾는 핀을 자꾸 사라지게 만들면 안 된다."

지번이 안 잡히면 **범위를 넓히되 어디까지 맞는 핀인지 밝힌다.**

| 단계 | 하는 일 | source | quality |
|---|---|---|---|
| 1 | 지번 그대로 | `address` | `verified` |
| 2 | 건물명 장소검색 (행정구역명은 차단) | `building` | `approximate` |
| 3 | 부번 떼고 본번만 (`891-171`→`891`) | `lot` | `approximate` |
| 4 | 리·동까지만 (어업권·건설기계는 지번이 없다) | `district` | `approximate` |
| 5 | 리·동도 못 찾으면 | 핀 없음 | |

**읍면 단위 핀은 만들지 않는다.** 그게 바로 이 격차의 거짓말이었다.
3·4단계는 **PNU를 싣지 않는다** — 옆 필지의 PNU를 쓰면 공시가격·건축물대장·
실거래가가 남의 땅 것으로 채워진다.

### ③ 읍면은 승격만 하는 게 아니라 **개명**도 한다

맞바꾸기로도 안 잡히는 것이 남았다. 성주군 **금수면 → 금수강산면**처럼 이름이
통째로 바뀐 경우다. 읍면 토큰을 아예 빼면 지도가 새 이름으로 찾아 준다.

```
경상북도 성주군 금수면 후평리 927-2  → 없음
경상북도 성주군 후평리 927-2         → 금수강산면 후평리 927-2 (지번 일치)
```

`apply_dropped_eup_myeon`. 시도·시군구는 절대 빼지 않는다.

### ④ 이미 박힌 것은 제자리에서 갈아끼웠다

`scripts/g12_refix_coords.py`. 좌표를 **지웠다 다시 찍지 않는다** — 지우면 다음
사이클까지 핀이 사라지고, 그 사이 옛 코드를 돌던 데몬이 다시 가짜를 박을 수 있다.
한 건씩 새로 물어보고 답을 받은 것만 덮어쓴다. 원본 값은 `data/g12-fake-coords-*.json`에
백업한다.

판정 기준을 **그때 던진 쿼리**(`geocode_query`)로 옮긴 것이 중요하다. 지금 코드의
`_extract_building_hint`로 판정하면 이 수정 뒤 0건으로 보여 "다 고쳐졌다"는
착각을 준다. `scripts/geocode_recheck.py`도 같이 고쳤다.

### ⑤ 밟은 함정 — `mark_coordinate_missing`은 좌표를 안 지운다

이름과 달리 `quality`만 바꾼다. 원래 호출자는 *좌표가 처음부터 없는* 물건이라
지울 점이 없어서 맞는 동작이었다. 그런데 **이미 박힌 좌표가 틀린 것으로 밝혀진**
경우에 그대로 쓰면 quality만 바뀌고 **가짜 핀이 지도에 그대로 남는다.** 실제로
1차 실행에서 9건이 '핀 없음'으로 기록됐는데 가짜 좌표를 달고 있었다.

게다가 `geocode_query` 기본값이 빈 문자열이라 **무엇이 가짜였는지 증거까지 지웠다** —
탐지 기준이 그 쿼리이므로 그 9건은 검사에서도 사라졌다. 백업 파일로 되살려 다시 돌렸다.

`clear_point=True`를 달았다(기본값은 예전 그대로). 회귀 테스트는
`tests/test_store.py::test_mark_coordinate_missing_can_clear_a_wrong_point`.

### 결과 (2026-09-17 실행 완료)

| | 건수 |
|---|---|
| 지번 정확(`verified`) — **PNU도 662건 새로 붙었다** | **662** |
| 옆 필지(`lot`) / 리 단위(`district`) | 12 / 13 |
| 핀 없음 | 6 |
| 옮겨간 거리 | 중앙값 2.65km · 최대 14.23km · **1km 넘게 틀려 있던 것 537건(78%)** |

가짜 좌표는 활성·비활성 모두 **0건**이다.

### 남은 것
- **핀 없는 6건**(활성 3) — **핀을 만들지 않기로 했다**(사용자 결정 2026-09-17).
  화성시 서신면 사곳리 2 · 통영시 산양읍 삼덕리 3 · 의정부시 태평로 76 1.
  면은 멀쩡한데(전곡리·궁평리·풍화리·의정부동은 다 잡힌다) **그 리·그 도로만
  브이월드에 없다.** 읍면 단위로 더 넓히면 여러 물건이 한 점에 뭉쳐 이 격차의
  거짓말과 같아진다. DB에는 `coordinate_quality='missing'`으로 적었고 snapshot
  payload도 `coordinate_source='none'`·`coordinate_quality='missing'`을 내보낸다.
  **웹(세션 D)이 이걸 '위치 미상'으로 목록에 드러내야 한다** — 지도에서 빠지되
  물건 자체는 사라지지 않게.
- **웹이 `coordinate_quality`를 쓰게 해야 한다(세션 D, G13).** 3·4단계 근사 핀이
  지금은 지번 핀과 똑같이 보인다. 사다리를 놓은 이상 이건 더 미룰 수 없다.
- 한 번 박힌 좌표를 다시 안 물어보는 구조는 그대로다. `approximate`는 기한을 두고
