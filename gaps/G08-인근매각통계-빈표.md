# G08. 인근매각통계 표가 3,892건 전부 비어 있다

**상태**: **해결됨** (2026-09-17, 세션 B) · **담당**: 세션 A→B · **우선순위**: 중

## 한 줄
법원이 주는 '동네 시세 통계'를 **머리글만 받아오고 있다.**

## 원인 — 2026-09-17에 실제 DOM을 보고 정정했다

**9/16에 적은 진단이 틀렸다.** `인근매각통계`라는 버튼을 누르는 게 아니다.

```
wq_uuid_1039          "인근매각물건사례"     ← 절 제목 (보임)
btn_srchNearHist      "검색"               ← **이것을 누른다**
tac_aroundGdsExmGrp   탭 3종               ← 누르기 전에는 display:none · 0x0
  ├ tab_tabs1  인근매각통계
  ├ tab_tabs2  인근매각물건
  └ tab_tabs3  인근진행물건   ← 9/16 문서에 없던 세 번째 탭
```

**탭을 직접 누르려 하면 영원히 기다린다.** 묶음이 `display:none`이라 탭이 0x0이고,
Playwright는 '보이고 눌릴 때까지' 기다리기 때문이다. 이걸 모르고 탭만 찾다가
탐사를 열네 번 돌렸다.

## 결과
표본 4,000건 중 **데이터 있음 0건 / 빈 표 3,892건.**

법원이 주는 칸: `기간 · 매각건수 · 평균감정가 · 평균매각가 · 매각가율 · 평균유찰횟수`
(옥션원은 같은 자리에 `입찰인원수`와 자체 추정가까지 붙인다 — 그건 우리가 못 만든다)

## 고친 방법

`_extract_item_detail`이 표를 긁기 전에 `_open_near_sales`를 부른다.
`btn_srchNearHist`를 `locator.click()`으로 누르고 **데이터가 도착할 때까지** 기다린다.

### 기다리는 조건을 세 번 틀렸다 — 이게 이 항목의 진짜 함정이다

묶음은 클릭 즉시 보이는데 **내용은 그 뒤에 온다.** 조건을 잘못 고르면 안 기다린
것과 같고, 그러면 **머리글 한 줄만 받고 성공으로 넘어간다.**

| 조건 | 왜 틀렸나 |
|---|---|
| 묶음이 `visible`이면 끝 | 묶음은 즉시 보인다 |
| 묶음에 `N개월`이 있으면 끝 | 기간 표기는 데이터 전부터 DOM에 있다 |
| 묶음에 `td`가 든 행이 있으면 끝 | **묶음 안에 표가 하나 더** 있고 이미 `td`를 갖고 있다 |

셋 다 클릭 직후 이미 참이라 16건을 재면 16건 모두 빈 표였다. 그런데
`except: return False`가 실패를 삼켜 **로그에는 아무것도 안 남았다** — `CLAUDE.md`
함정 ④의 '조용히 0건'을 새로 만든 셈이다. 6건만 보고 커밋했으면 '해결됨'이라
적힌 채 한 건도 안 채워졌을 것이다.

추측을 그만두고 DOM 변화를 찍어서 조건을 정했다.

```
[클릭 전]   통계표 tr 1 · td행 0      다른 표 tr 1 · td행 1   ← 범인
[+0ms]     통계표 tr 1 · td행 0
[+500ms]   통계표 tr 4 · td행 3      ← 데이터 도착
```

최종 조건은 **읽어 갈 그 표 하나** — 캡션에 `매각가율`이 든 표에 `td` 행이 생길
때까지다. `extract_tables`가 읽는 것과 같은 것이라 지표와 코드가 어긋날 수 없다.

### 나머지 두 탭은 일부러 안 누른다

실측: `인근매각물건` **237행** · `인근진행물건` **196행**. 물건 하나에 수백 행이면
상세 payload가 감당이 안 된다. 우리가 원한 것은 그것을 요약한 통계 네 줄이다.

### 소급은 안 된다

**종국된 사건은 물건상세가 아예 안 열린다**(`물건상세조회` 버튼이 비활성).
이미 쌓인 33,555건의 빈 표는 그대로 남고, 앞으로 수집하는 진행 물건부터 채워진다.
