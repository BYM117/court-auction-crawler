# G11. 법원 공식 집계와 대조해본 적이 없다 — '모르는 것'을 찾는 유일한 장치

**상태**: 진행 중 (도구 완성 2026-09-17 · 첫 온전한 대조는 2026-10-01) · **담당**: 세션 C · **우선순위**: 최상위 급

## 한 줄
지금 우리 검증은 **전부 '이전 우리 값'과 비교**한다. 처음부터 적게 긁었으면 영원히 모른다.

## 왜 최우선인가
나머지 항목은 전부 **'이미 아는 문제'를 고치는 일**이다.
**G11만이 모르는 문제를 스스로 드러나게 한다.**

2026-09-16에 다른 세션이 찾은 버그가 정확히 그런 종류였다 —
매각결과 표 헤더의 `rowspan=3` 처리 오류로 **페이지마다 첫 물건이 조용히 사라지고 있었다**
(서울중앙 179→174, 속초 11→10). **예외도 로그도 없었다.**
우리 값끼리 비교하는 한 영원히 안 걸렸을 것이다.

## 법원이 주는 것

```
매각통계 > 연도별 / 법원별 / 지역별 / 용도별매각통계
용도별은  PGJ164M01.xml
```

법원·기간을 주면 이걸 돌려준다.
```
물건용도 | 경매건수 | 매각건수 | 감정가 | 매각가 | 매각율 | 매각가율
아파트   |    373  |    136  | 228,372,047,500 | 218,189,678,332 | 36.5% | 95.5%
        (서울중앙지방법원, 2025.08~2026.09)
```

화면에 통계용어 정의도 있다 — `경매건수 = 매각기일(입찰·유찰 포함) 및 매각된 물건의 건수`.

## ★ 실측 (2026-09-17, 세션 C) — 대조 도구를 만들었고, A는 필요 없어졌다

`scripts/baseline_compare.py`

```bash
.venv/bin/python scripts/baseline_compare.py --fetch 202608   # 법원 통계 받기
.venv/bin/python scripts/baseline_compare.py 202608           # 대조
.venv/bin/python scripts/baseline_compare.py --check          # 자가 점검
```

### 세션 A를 안 기다려도 된다

원래 계획은 *"A가 통계를 긁고 C가 대조한다"* 였다. **받는 쪽이 생각보다 쌌다.**
화면을 60번 검색할 필요 없이 JSON API 하나면 된다.

```
POST /pgj/pgj164/selectRletCortDspslStats.on
{"dma_search":{"searchType":"01","cortOfcCd":"B000210",
               "adongSdCd":"","adongSggCd":"","startDate":"202608","endDate":"202608"}}
```
법원 코드는 `POST /pgj/pgjComm/selectCortOfcCdLst.on` (빈 본문)이 준다 —
`서울중앙지방법원 = B000210` 꼴로 60개.

**curl은 WAF가 막는다**(실측: `Web firewall security policies have been blocked`).
브라우저 세션이 있어야 해서 Playwright로 페이지를 한 번 열고 그 안에서 API를 부른다.
60개 법원에 250ms 간격, 한 번에 20초쯤. `crawler.py`는 건드리지 않았다.

### 창은 한 달이고, **다음 달 1일에 확정된다**

응답에 `frstInptDt: "20260901"`이 붙는다. 화면도 *"2026년 09월 01일 기준"* 이라 적는다.
**9월치는 10월 1일부터 받을 수 있다.** 기간은 1년 이내만 조회된다.

### 정의가 우리와 다르다 — 두 군데

| | 법원 | 우리 |
|---|---|---|
| 경매건수 | 입찰(유찰 포함) 및 매각된 물건 | `auction_sale_results`의 `유찰`+`매각` 행 |
| 매각건수 | **최종 물건상태**가 `매각·매각허가결정·대금납부` | **기일 결과**가 `매각` |

매각건수는 기준이 아예 다르다. **대금미납으로 재매각된 물건이 서로 어긋난다.**
그래서 이 도구는 **경매건수(기일 수)** 로 대조한다. 그쪽이 정의가 맞는다.

### ★ 기준선 숫자 — **100~102%가 정상이다**

202608을 대조했다. 우리 기일 데이터는 **8/20에 시작**해서(이레 창이라 8/13부터)
8월을 처음부터 보지 못했다. 그래서 전국 58.6%, 중앙값 55.6%가 나온다 —
**이건 누락이 아니라 시작 시점이다.**

그런데 **8/13 이후에만 기일이 있었던 법원 5곳**은 이렇게 나왔다.

| 법원 | 법원통계 | 우리 | 비율 |
|---|---|---|---|
| 남양주지원 | 339 | 339 | 100% |
| 영덕지원 | 85 | 86 | 101% |
| 강릉지원 | 161 | 163 | 101% |
| 거창지원 | 94 | 96 | 102% |
| 남원지원 | 86 | 84 | 98% |

**온전히 받으면 100~102%다.** 우리가 조금 많은 것은 법원 통계에서 취하 등이 빠지기
때문으로 보인다. **이 5곳이 기준선이다 — 95% 아래면 그 법원에서 새고 있다.**

### 깃발 8개는 전부 오탐이었다 — 부분 달로는 못 가른다

낮게 걸린 법원을 하나씩 열어보니 전부 **기일 날짜 분포**였다.

```
영동지원   0%  — 8월 기일이 8/4·8/11뿐. 우리 창(8/13~) 밖이다. 9월엔 110행 정상
밀양지원  25%  — 8월 기일 8/3·…·8/31 중 8/31만 받았다
안동지원  25%  — 8/24만 받았다
```
**부분 달에서는 '적게 받은 법원'과 '기일이 일찍 있던 법원'을 가를 수 없다.**
그래서 도구가 부분 달이면 경고를 먼저 띄운다.

### 그래서 남은 것은 시간뿐

**2026년 9월이 우리가 처음부터 끝까지 본 첫 달이다.** 그 통계는 **2026-10-01**에 나온다.
그날 아래를 돌리면 G11이 처음으로 제 일을 한다.

```bash
.venv/bin/python scripts/baseline_compare.py --fetch 202609
.venv/bin/python scripts/baseline_compare.py 202609
```

**그때 95% 아래로 떨어지는 법원이 있으면, 그게 우리가 몰랐던 손실이다.**

2. ~~(세션 C) 우리 집계와 대조한다~~ → **해결됨 2026-09-17.** `scripts/baseline_compare.py`.
